# Маршрут ручного ревью

Этот skill строит навигационную карту для ручного изучения Git-изменений. Он не выполняет code review вместо пользователя, не ищет полный список ошибок и не делает вывод, что код готов к merge. Цель - помочь быстро понять замысел изменения, выбрать верный порядок чтения и сосредоточить ручное внимание на важных местах.

Основной способ запуска - явный: `/review-guide` или эквивалентный механизм Codex. После запуска сначала выбери scope, и только затем изучай изменения.

## Выбор scope

Запусти исполняемый скрипт `scripts/select-review-scope.sh` по пути относительно каталога этой skill, назначив рабочим каталогом проверяемый Git-репозиторий. Он выводит подсказки в stderr, а stdout содержит только машинно-читаемые строки `КЛЮЧ=ЗНАЧЕНИЕ`.

Разбери stdout как данные, не передавай его в `eval`. Используй `BASE` и `HEAD` как границы Git range. Для режима `commits` поле `COUNT` фиксирует выбранное число коммитов. Если скрипт не смог определить base branch, сообщи понятную причину и запроси у пользователя ветку-основу; не выбирай её произвольно.

Скрипт только выбирает scope. Не поручай ему анализ diff и не изменяй репозиторий во время выбора.

## Сбор контекста

После выбора scope самостоятельно:

1. Получи список изменённых файлов и полный diff выбранного диапазона.
2. Просмотри историю коммитов диапазона, если она проясняет замысел.
3. Прочитай окружающий контекст изменённых функций, классов и модулей.
4. При необходимости проследи вызовы изменённых частей и их архитектурную роль.
5. Найди связанные тесты и проверь, какое поведение они закрепляют.

Не ограничивайся строками diff и не исследуй несвязанные части репозитория без причины. Сначала сформулируй смысл изменения на высоком уровне, затем выстрой порядок чтения от сути к деталям. Не используй механический порядок файлов: точкой начала может быть domain model, контракт API, миграция, точка входа или основная логика - то, что лучше объясняет конкретное изменение.

## Формат ответа

Верни компактный результат с заголовком `## Маршрут ревью`.

### Суть изменения

В 2-5 предложениях объясни задачу, изменившееся наблюдаемое поведение и расположение основной логики. Не пересказывай сообщения коммитов.

### Как читать изменение

Дай нумерованный маршрут в концептуальном порядке. В каждом пункте укажи реальный файл, символ и актуальный диапазон строк текущего checkout, например:

```text
1. src/example/service.py - ExampleService.process()
   строки 120-178

   Зачем смотреть:
   Здесь находится основная логика нового поведения.

   Обрати внимание:
   - ...
   - ...
```

Предпочитай функцию, класс или метод вместе со строками, а не только путь к файлу. Помечай критические участки словами "Критический участок" или "Стоит внимательно проверить". Вспомогательные части обозначай как "Можно просмотреть после основной логики".

### Ключевые инварианты

Перечисли только свойства, действительно затронутые изменением. Для каждого существенного свойства по возможности укажи код, который его обеспечивает. Не придумывай инварианты, не подтверждённые кодом или diff.

### На что обратить особое внимание

Выдели только относящиеся к изменению места, где особенно важна ручная проверка: конкурентный доступ, транзакции, переходы состояний, границы безопасности, удаление данных, идемпотентность, обработка ошибок, внешние интеграции, обратная совместимость, миграции или контракты API. Если заметно очевидно подозрительное место, отметь его как участок для проверки, но не превращай ответ в автоматическое ревью или перечень багов.

### Тесты

Свяжи важные тесты с проверяемым поведением в форме `путь::тест → поведение`. Если важное изменённое поведение не покрыто тестом, прямо отметь это.

### Второстепенные изменения

Кратко перечисли механические, конфигурационные, документационные, сгенерированные или fixture-изменения, которые можно изучить после основной логики. Если их нет, не добавляй этот раздел.

## Границы работы

Не переписывай код, не исправляй проблемы, не создавай коммиты и не утверждай, что изменение правильное или готово к merge. Не перечисляй каждый файл ради полноты и не пересказывай diff построчно.

После выдачи маршрута сохраняй собранный контекст в текущей сессии. На обычные последующие вопросы пользователя о причинах решений, транзакциях, конкурентном доступе, версиях или поведении внешнего API отвечай по уже изученному контексту без повторного запуска `/review-guide`. Если для ответа нужен дополнительный связанный код, изучи его.
