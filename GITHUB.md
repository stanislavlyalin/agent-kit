# Оформление задач и PR в GitHub

Правила применяются при подготовке описаний задач и PR. Требования к языку и стилю задаёт [LANG.md](LANG.md).

## Формат выдачи

Для задачи выдавать поля в следующем порядке:

1. Ветка git.
2. Заголовок задачи.
3. Стандартные теги GitHub.
4. Описание в Markdown.

Для PR выдавать аналогичные поля:

1. Ветка git.
2. Заголовок PR.
3. Стандартные теги GitHub.
4. Описание PR в Markdown.

В поле ветки указывать исходную ветку изменения. Описание предоставлять отдельным блоком кода `markdown`, чтобы его можно было скопировать в GitHub. Название ветки, заголовок и теги выводить вне этого блока.

## Содержание

Заголовок задачи описывает конкретную проблему или требуемый результат. Описание содержит проблему, необходимые изменения и проверяемые критерии приёмки.

Заголовок PR описывает получившееся изменение. Описание объясняет итоговое поведение, существенные изменения и выполненные проверки. Не включать историю диалога и отвергнутые варианты, если они не объясняют важное решение.

В PR, закрывающем задачу, обязательно добавлять отдельный абзац `Closes #<номер>`. Подставлять известный номер задачи; если он неизвестен, оставлять явный placeholder `Closes #<номер>`, не придумывать номер.

## Переносы строк

Каждый абзац и каждый пункт списка записывать одной строкой без искусственных переносов по ширине. Сохранять заголовки, пустые строки и структуру Markdown. Это правило относится к подготовленным описаниям, включая текст внутри блока `markdown`; длинные строки допустимы.

## Теги и публикация

Выбирать подходящие стандартные метки GitHub: `bug` для ошибки, `enhancement` для улучшения, `documentation` для документации. Не добавлять метки, не относящиеся к изменению. Перед реальной публикацией проверять доступность выбранных меток в целевом репозитории.

Подготовка текста не означает создание задачи или PR в GitHub. Создавать или публиковать их только в рамках соответствующего запроса пользователя.
